# VISION — 제품 방향

- 작성: 2026-10-05
- **이 문서는 방향 기록이다. 현재 작업 트랙(M2 자동화)을 바꾸지 않는다.**
  로드맵·일정은 [ROADMAP.md](ROADMAP.md), 현재 상태는 [PROJECT_STATUS.md](PROJECT_STATUS.md).
- 경쟁 제품 서술은 2026-10-05 시점의 방향 설정용 정리이며 **일차 출처로 재확인하지 않았다.**
  의사결정에 쓰기 전에 각 제품의 현재 기능·가격을 직접 확인할 것.

---

## 1. 한 줄 정의

**장면에서 플레이 가능한 캐릭터를 만든다.**

영상 한 편을 넣으면 외형·골격·동작을 갖추고 게임 엔진에서 바로 움직이는 캐릭터가 나온다.
"3D 모델"도 "모션 데이터"도 아니고, **그 둘이 서로 맞물린 상태로** 나오는 것이 핵심이다.

## 2. 왜 빈칸인가

지금 시장은 둘로 갈라져 있다.

| 갈래 | 대표 | 주는 것 | 안 주는 것 |
|---|---|---|---|
| 이미지 → 3D | Meshy · Tripo | 메쉬 + 텍스처, 자동 리깅, **프리셋 동작 라이브러리** | 그 캐릭터 고유의 동작. 걷기·달리기는 남의 모션이다 |
| 영상 → 모캡 | DeepMotion · Move AI | 영상에서 뽑은 **동작 데이터** | 캐릭터 외형. 내 캐릭터에 붙이려면 리타게팅이 필요하다 |
| 영상 → CG 영상 | Wonder Studio | 완성된 **영상** | 게임에 넣을 에셋이 아니다. 출력이 픽셀이지 메쉬가 아니다 |

양쪽을 사서 붙이면 되지 않느냐 — 그 접착이 바로 리타게팅이고, 이 프로젝트가 v2·v3에서
세 가지 방식으로 시도해 **전부 실패한 지점**이다 (PROJECT_STATUS 3절).

**빈칸은 네 가지가 동시에 성립하는 자리다.**

1. **임의 동작** — 프리셋이 아니라 그 영상에 담긴 바로 그 움직임
2. **외형-동작 정합** — 같은 사람에게서 나온 외형과 동작이라 체형이 어긋나지 않는다
3. **리타게팅 소거** — 골격을 SMPL로 통일해 변환 단계 자체를 없앴다 (v4의 핵심)
4. **검증 내장** — 게이트가 단계마다 수치로 판정한다. 품질이 운에 맡겨지지 않는다

4번은 경쟁 제품에서 잘 보이지 않는 축이다. 생성형 도구는 결과가 나쁘면 사람이 보고 다시
돌리는데, 양산에서는 그 사람이 병목이 된다.

### 모캡 엔진 선택 — WHAM 이 설계의 전제다

3번(리타게팅 소거)이 가능한 이유는 모캡 엔진 선택에 있다. 같은 "영상 → 동작"이라도
출력 형식이 다르고, 그 차이가 설계를 가른다.

| | 출력 | 골격 | 결과 |
|---|---|---|---|
| 상용 모캡 (DeepMotion · Move AI · Rokoko) | **동작만** (FBX/BVH) | 제품 고유 리그 | 내 캐릭터에 붙이려면 **리타게팅 필요** |
| **WHAM** (채택) | **SMPL 네이티브** — pose + **betas** | SMPL 24본 | 외형 경로도 SMPL 로 세우면 **변환이 사라진다** |

핵심은 `betas` 다. 상용 모캡은 동작을 주지만 **체형을 주지 않는다.** WHAM 은 pose 와 함께
betas(체형 파라미터)를 내므로, 그 betas 로 외형 경로의 골격을 세우면 양쪽이 같은 골격이
된다 — 이것이 v4 전환의 전부다 (PROJECT_STATUS 4절).

따라서 상용 모캡으로 갈아끼우는 선택지는 **없다.** 바꾸는 순간 리타게팅이 돌아오고,
v2·v3 에서 세 번 실패한 그 자리로 되돌아간다. 모캡 엔진 교체를 검토한다면 **SMPL 계열
출력 여부가 1차 조건**이다.

## 3. 입력 2모드

| 모드 | 입력 | 성격 |
|---|---|---|
| **A. 영상** | 영상 1편 | **간판이자 차별점.** 동작이 영상에서 직접 나온다 |
| **B. 이미지 + 프롬프트** | 레퍼런스 이미지 + 동작 설명 | 내부에서 영상을 생성해 A로 흘려보낸다 |

B는 A의 앞단이지 별도 경로가 아니다. 사용자가 영상을 못 구할 때 "이 캐릭터가 이렇게
움직이는 영상"을 만들어 주는 것이고, 그 뒤는 A와 같다.

B는 **입력 분리 설계**와 같은 기반 위에 선다 — 외형은 선명한 레퍼런스 이미지에서(S3),
동작은 영상에서(S5) 가져오고 정렬 기준만 맞추는 구조다. 입력 분리가 실증되면 B는
그 구조의 자연스러운 확장이 된다.

## 3.5. 모션 소스 대안 — 향후 검토

현재 모션 소스는 영상(WHAM) 하나다. 대안이 하나 있다.

**텍스트 → 모션.** 동작 설명을 넣으면 SMPL 시퀀스를 내주는 모델이 존재한다. 영상 수급
부담이 사라지는 것이 장점이다. 다만 두 가지 제약이 있다 — **어휘가 제한적이고**(학습
데이터에 있는 동작 범위를 벗어나기 어렵다) **품질 편차가 크다.**

**영상 경로에는 대안에 없는 이점이 있다 — 사람이 확인할 수 있는 중간물이 남는다.**
원본 영상과 재투영 오버레이를 나란히 놓고 "이 동작이 맞다"를 눈으로 판정할 수 있다.
텍스트 입력은 대조할 원본이 없어 "요청한 동작이 나왔는가"를 사람이 직접 보는 수밖에 없다.
검증 내장(2절 4번)을 내세우는 제품으로서는 이 차이가 작지 않다.

결론은 **보류하고 지켜본다**이다. 모드 B(이미지 + 프롬프트)가 내부 영상 생성을 거치는
것도 같은 이유다 — 중간에 영상이 끼면 사람이 볼 것이 생긴다.

## 3.7. 모션 상호운용 — 골격 통일의 두 번째 배당

리타게팅 소거(2절 3번)는 파이프라인 안의 이점이지만, 같은 통일이 **파이프라인 밖으로도**
열린다. 모든 산출물이 SMPL 24본을 쓰므로 **캐릭터 사이에 동작을 옮길 수 있다.**

옮길 때 손대는 것은 하나뿐이다.

| | 처리 |
|---|---|
| `pose` (24관절 회전) | **그대로 쓴다.** 회전은 체형과 무관하다 |
| `trans` (루트 이동) | **신장비로만 스케일.** 키가 다르면 보폭이 달라야 한다 |

좀비 4종이 서로의 걸음걸이를 공유하고, 군중 NPC 가 동작 하나를 돌려 쓰는 것이 이 위에
선다 (4절). 외부 자산도 같은 문으로 들어온다 — **AMASS 같은 공개 SMPL 모션 데이터셋을
그대로 상속**할 수 있다. 우리가 만든 캐릭터에 공개 모션을 입히는 데 변환 단계가 없다.

**전제가 하나 있다 — rest 자세가 캐릭터마다 같아야 한다.** 지금은 그렇지 않다. 리그의
rest 가 각 캐릭터의 키프레임 자세라, A 의 pose 를 B 에 넣으면 B 의 rest 기준으로 해석돼
어긋난다. 상호운용이 성립하려면 **T포즈 rest 로 통일**해야 한다.

즉 **EH-211(T포즈 rest 리그 재생성)은 Unity Humanoid 호환 과제가 아니라 상호운용의
전제 조건이다.** 지금까지 "에셋 상품성 관점 개선 과제"로 두었으나, 모션 공유와 외부
모션 상속이 제품 방향에 들어온 이상 **근거를 격상한다.**

## 4. 타깃

**인디 개발자 · 프로토타이핑 · 군중 NPC.**

AAA는 캐릭터 하나에 아티스트가 붙는다. 우리가 겨루는 자리가 아니다. 반대로 **같은 품질의
캐릭터가 여러 개 빨리** 필요한 곳이 우리 자리다.

**SMPL 골격 통일이 여기서 이점이 된다.** 모든 산출물이 같은 24본 골격을 쓰므로 캐릭터
사이에 동작을 섞어 쓸 수 있다 — 좀비 4종이 서로의 걸음걸이를 공유하는 식이다. 군중 NPC는
이 공유가 곧 제작비다.

## 5. 단계

```
M2 자동화 완성          원커맨드 E2E · 게이트 전체 작동 · Docker 재현
   ↓
입력 분리 (v4.5)        S3 는 레퍼런스 이미지, S5 는 영상. 모드 B 의 기반
   ↓
웹 쇼케이스 + 제어 UI    3D 뷰어·before/after / 업로드·진행·체크포인트 승인
   ↓
공개 서비스             ** 라이선스·비용 해소 후 **
```

**공개 서비스는 조건부다.** 두 가지가 풀려야 한다.

- **SMPL 라이선스** — 무료 판은 비상업 연구용이다. 상업 배포에는 Meshcapade 라이선스가
  필요하다 (PROJECT_STATUS 7절 리스크).
- **GPU 비용** — 현재 1편당 Pod 12분이다. 사용자가 늘면 그대로 원가가 된다.

둘 중 하나라도 미해결이면 쇼케이스·내부 도구까지만 간다. 순서를 바꾸지 않는 이유는,
서비스를 먼저 열고 라이선스를 뒤에 푸는 선택지가 없기 때문이다.
